# Layer-by-layer analysis of the captured traffic

Based on pharmacy_remote_capture.pcapng, traffic generated by
capture_session.py against the remote MCP server on Render.

## Data link layer

Each frame captured on this interface corresponds to Ethernet, visible
as the "Ethernet II" block in each packet's detail. It contains the
source MAC (the local network interface running capture_session.py)
and the destination MAC, which in this case is the local gateway or
router, not the remote server, since the two ends sit on different
networks and the final destination is not reachable on the same link.

## Network layer

Each packet uses IP as the network layer protocol. The source IP is
the public or private address of the machine running
capture_session.py, and the destination IP corresponds to Render's
edge network resolving the *.onrender.com domain.

## Transport layer

TCP is the transport protocol, visible in the three-way handshake at
the start of the capture, SYN, SYN-ACK, ACK, before any application
data. The destination port is 443, standard for HTTPS. Over that same
TCP connection, the TLS handshake is then established, ClientHello,
ServerHello, Certificate, and key exchange, before any application
layer byte can travel. Thanks to the key file exported via
SSLKEYLOGFILE, Wireshark reconstructs the encrypted content of the
later TCP segments and shows the application traffic in plain text
inside the "Decrypted TLS" panel.

## Application layer

Over the same established TCP and TLS connection, two application
protocols are layered on top of each other. HTTP/1.1 carries each
message, visible as POST requests with Content-Type application/json
and Content-Length headers. Inside the body of each request and
response travels JSON-RPC 2.0, the actual application protocol of MCP,
each message with its jsonrpc field, and depending on the case, id,
method, params, result, or error. This matches exactly what the
project statement describes, MCP runs on top of JSON-RPC, which in
turn can be transported over HTTP in the remote case or directly over
stdio in the local case.

## Comparison with the local transport

Unlike the local server, where JSON-RPC travels directly over the
process's stdio with no networking layers involved beyond the
operating system itself, the remote server needs all four layers,
data link, network, transport, and application, for the same JSON-RPC
message to travel from one end to the other. The message content
itself (protocol.py) is identical in both cases, only what carries it
underneath changes.
